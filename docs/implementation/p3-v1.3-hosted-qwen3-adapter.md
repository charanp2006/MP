## 1. Objective

Replace the outdated local llama-style planner path with provider adapters for hosted Qwen3 inference while preserving the deterministic stub and historical Ollama adapter for compatibility.

This phase implements the code path only. It does **not** claim successful real Qwen3 inference because no endpoint, model revision, paid provisioning, or API key was approved or used.

## 3. Data and Control Contracts

### Provider selection

`build_planner` accepts these `agent.runtime` / `agent.provider` values:

- `stub` — deterministic offline planner.
- `ollama` / `qwen3` — historical local adapter, retained for compatibility only.
- `huggingface` — hosted primary. With `fallback_provider: openrouter`, uses a provider chain.
- `openrouter` — hosted backup, with deterministic stub fallback.

### Request contract

Both hosted providers send an OpenAI-compatible chat-completions JSON body:

- `model`: pinned model ID; HF includes `@revision` when configured.
- `messages`: existing system prompt plus bounded user prompt.
- `temperature`, `max_tokens`, `stream: false`.

Credentials are read only from environment variables:

- Hugging Face: `HF_ENDPOINT_URL`, `HF_TOKEN`, `HF_MODEL_ID`, `HF_MODEL_REVISION`.
- OpenRouter: `OPENROUTER_ENDPOINT_URL`, `OPENROUTER_API_KEY`, `OPENROUTER_MODEL`, `OPENROUTER_MODEL_REVISION`.

Configured endpoint/model values are defaults; explicitly set environment variables override them for runbook use.

### Response contract

The adapter accepts:

- OpenAI-compatible `choices[0].message.content` and `choices[0].text`.
- Hugging Face `generated_text` responses.
- Existing Ollama-style `message.content` responses.

The content must be JSON matching the strict `Plan` schema. `PlanValidator`, PPO reconciliation, the SLA guard and the executor allowlist remain downstream safety boundaries.

### Failure contract

- `429`, `408`, `5xx`, timeout and network failures are retryable within `max_retries`.
- `401`, `403`, malformed JSON, invalid plans and unexpected response shapes are not retried.
- Errors are redacted before telemetry.
- Provider chain order is Hugging Face → OpenRouter → deterministic stub.
- Planner output never bypasses validation or execution safety.

### Telemetry

`PlannerCallRecord` now records provider, model, revision, prompt version, status, latency, fallback state, redacted reason, strategy, plan code, token usage and attempts.

## 4. How to Run and Verify

```bash
python -m pytest --disable-warnings -q tests/test_agent_m3.py tests/test_agent.py tests/test_agent_m4.py
python -m pytest --disable-warnings -q
git diff --check
python -m scripts.evaluate_planner --runtime stub --out-dir results/planner/stub
```

Hosted real-inference smoke commands and beginner HF setup are documented in `docs/qwen3-hf-smoke-verification-guide.md` and `docs/qwen3-hosted-inference-plan.md`. They are not executed in CI and require owner-supplied credentials and an approved endpoint:

```bash
python -m scripts.evaluate_planner --runtime huggingface --out-dir results/planner/huggingface
python -m scripts.evaluate_planner --runtime openrouter --out-dir results/planner/openrouter
```

## 5. Test Coverage

- Hugging Face chat response parsing, model revision and token usage telemetry.
- OpenRouter bearer token and model loaded from environment; secret absent from telemetry.
- HTTP 429 retry with bounded attempts.
- HTTP 401 auth failure with no retry and redacted reason.
- Malformed JSON classified as non-retryable invalid output.
- Provider chain fallback from Hugging Face to OpenRouter with fallback telemetry.
- Final fallback to the deterministic stub after both hosted providers fail.
- Existing Ollama and stub planner tests remain passing.

All hosted-provider tests use mocked HTTP responses. No external endpoint was contacted.

## 6. Limitations and Next Steps

- Real Qwen3 inference is **not verified**; M3 is not complete until an owner-approved hosted request succeeds through this code path.
- Exact HF model/revision, endpoint product, OpenRouter slug, quota and cost remain owner decisions.
- No secret manager integration was added; environment-variable handling follows the existing plan and must be protected by deployment practice.
- Usage telemetry is recorded when present but may be absent on some endpoints.
- Planner-to-PPO influence remains the existing soft-feedback contract from V1; the explicit advisory contract belongs to M5.
- Next implementation milestone after owner verification should be M5 integration contract, then M4 PPO rigor.
