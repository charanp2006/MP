## 1. Objective and scope

Answer one question for the control loop: **"what invocation load will hit each
function over the next N control intervals?"** — early enough that capacity can
be positioned before demand arrives (proactive prewarm/scale instead of
reactive cold starts).

Scope of this document: the path

```
trace → ingestion → preprocessing → features → windows → TFT → forecast JSON
```

and the hand-off of that forecast to the (future) planning/control layers.

---

## 2. Conceptual foundations

### 2.1 Where prediction sits
The closed loop (`AGENTS.md`, `docs/architecture.md`):

```
traffic → ingest → preprocess → FEATURES → TFT forecast → Qwen3 plan
  → PPO action → validate/SLA guard → execute (K8s/OpenFaaS) → observe → feedback
```

Prediction is the bridge between *observation* and *decisions*: scaling is
committed **before** demand lands, so forecast quality sets the ceiling on
energy/SLA performance.

### 2.2 Prerequisites
- **Time-series learning:** rows are not i.i.d.; order matters → never
  random-shuffle splits; the model needs a sequence, not a single row.
- **Fixed control interval:** `control.interval_seconds: 60` is shared by
  resampling, forecasting and control, so one forecast step = one control step.
- **History → horizon:** `history_window = 30` past intervals → `horizon = 5`
  future intervals.
- **Leakage:** any future information in inputs or scaling statistics is a bug
  (the property enforced by T03).
- **Energy/SLA/cold-start coupling:** more warm capacity ↓ latency and cold
  starts but ↑ energy; prediction lets the controller pre-position capacity
  rather than react.
- **Batch vs online:** this prototype is **offline/batch**; online streaming
  inference is a later integration.

### 2.3 Vocabulary

| Term | Meaning |
|---|---|
| Trace | Tabular workload records (timestamp, function, metrics) |
| Window | `history` input steps → `horizon` target steps |
| Split | chronological train/val/test = 70/15/15 |
| Scaler | per-column z-score **fit on train only** |
| Covariate | auxiliary input channel (CPU, memory, time) |

## 3. Workload ingestion layer

### 3.1 API Gateway / Load Balancer — operational mechanics (conceptual)
In the target architecture (`final.png` step 1, `docs/architecture.md`), the
gateway + LB sit in front of the functions and would:

1. **Terminate connections** (TLS) and authenticate/quota tenants.
2. **Distribute requests** across replicas (round-robin / least-connections /
   consistent hashing) to avoid saturation.
3. **Health-check + circuit-break** unhealthy replicas out of rotation.
4. **Rate-limit / admission-control** to protect the SLA during bursts.
5. **Emit per-request telemetry** (timestamp, function, status, duration,
   tenant/session) that becomes the workload trace.

In a live deployment the gateway is therefore the **producer** of ingestion
records.

### 3.2 Status in this prototype (important)
The gateway/LB are **not running infrastructure**. Per `project.md` §9.6 and
`plan.md` P1, they are **deployment context**: for the prototype the ingestion
boundary stands in for them.

- **Offline (default):** `data.source: sample` → `data/sample.py`.
- **File:** `data.source ≠ sample` → `read_trace` (`data/ingestion.py:50`).
- **Azure Functions traces** are the intended real source, but **data-source
  only** — not the execution platform. No dataset is committed yet.

### 3.3 Ingestion implementation
`load_trace` (`data/ingestion.py:57`) selects the source and always routes
through `validate_trace` (`:26`):

- **Required:** `timestamp`, `function_id`, `invocation_count`.
- **Optional:** duration, CPU, memory, active/warm containers, cold starts,
  latency, P95, power.
- **Validation (FR-01):** DataFrame check; parseable timestamps with no NaT;
  `function_id` → string; numeric `invocation_count`; violations raise
  `TraceValidationError` (fail closed; traces are untrusted).
- `summarize_trace` (`:73`) emits JSON provenance: rows, functions, time
  range, columns, normative present/missing.

## 4. End-to-end: ingestion → prediction

Orchestrated by `data.pipeline.run` (`data/pipeline.py:15`):

| # | Stage | Function | Transformation | Output |
|---|---|---|---|---|
| 1 | Load + validate | `load_trace` / `validate_trace` | schema/dtype checks | raw trace |
| 2 | Summarize | `summarize_trace` | provenance JSON | `ingest` report |
| 3 | Sort (D01) | `sort_chronological` | stable `(timestamp,function_id)` | ordered |
| 4 | Dedupe (D02) | `deduplicate` | first/last/mean on key | unique |
| 5 | Outliers (D04) | `repair_outliers` | out-of-range → NaN | sanitized |
| 6 | Resample | `resample_frame` | 60 s bins; sum counts, mean metrics | fixed cadence |
| 7 | Fill (D03) | `fill_missing` | zero counts; ffill→bfill metrics | dense |
| 8 | Features | `build_features` | lags, rolling, temporal, system | feature frame |
| 9 | Window/split/scale | `make_forecast_data` | per-function chronological split + windows + train-fit scaler | `ForecastData` |
| 10 | Train | `train_tft` | MSE on scaled target, best-val checkpoint | checkpoint |
| 11 | Infer | `forecast` | forward + unscale | forecast JSON |

Default 7-day synthetic sizes: raw **60,480** → resampled **30,240** →
features **30,153**.

## 5. Model specifications

### 5.1 Model: compact Temporal Fusion Transformer
`TemporalFusionTransformer` (`forecasting/tft_model.py:76`) — a compact,
dependency-free PyTorch reimplementation retaining the defining TFT
ingredients (per `docs/architecture.md` §5, `docs/design.md` §6).

**Forward pass / shapes** (history 30, horizon 5, 7 channels, d_model 32, 2 heads):

```
Input (B, 30, 7)
  │ VariableSelectionNetwork (tft_model.py:51)
  │   7 × Linear(1→32); softmax weights over features per step; GRN
  │   → (B, 30, 32) + interpretable feature weights
  ├─ LSTM(32→32)                 → (B, 30, 32)
  ├─ MultiheadAttention(2)       → (B, 30, 32)  (self-attention over time)
  ├─ residual + GRN(32)          → (B, 30, 32)
  │ head: pool(last + temporal mean) → GRN → Linear(→5)
  ▼
Output (B, 5)   [scaled invocation_count for t+1 … t+5]
```

**Building blocks**
- `GatedResidualNetwork` (`:28`): ELU-linear + dropout + `sigmoid` gate + skip
  + `LayerNorm`.
- `VariableSelectionNetwork` (`:51`): learned softmax over input features per
  timestep (interpretable importance).
- **LSTM encoder:** short-term dynamics.
- **Multi-head self-attention:** long-range temporal context.
- **Forecast head:** combines recency (last state) + trend (temporal mean).

**Input channels = 7**, not the full 24-column feature store:
`invocation_count` + `covariates` (`cpu_utilization`, `memory_utilization`,
`active_containers`, `hour`, `day_of_week`, `peak_period`). Temporal lag/rolling
structure is learned internally rather than fed as pre-lagged channels.

### 5.2 Training methodology
From `train_tft` (`forecasting/train.py`) and `configs/project.yaml`:

| Aspect | Value |
|---|---|
| Loss | MSE on scaled target |
| Optimizer | Adam, lr `1e-3` |
| Epochs / batch | `8` / `64` |
| Gradient clipping | norm `1.0` |
| Seed | `42` (numpy + torch) |
| Split | chronological `70/15/15` (train < val < test) |
| Selection | best validation-loss checkpoint |
| Normalization | per-column z-score, **fit on train split only** |
| Checkpoint | `models/tft_checkpoint.pt` (state + feature list + scaler stats) |

Training batches are shuffled (each *sample* is time-contained); **split
boundaries are never shuffled**.

### 5.3 Evaluation (T04)
`regression_metrics` (`forecasting/evaluate.py:38`) on the **inverse-scaled**
target: **MAE**, **RMSE**, **MAPE** (MAPE skips denominators ≤ 1e-6 — unstable
near zero load).

### 5.4 Forecast output contract (`docs/design.md` §7)
`forecast` (`forecasting/inference.py:41`):

```json
{ "forecast_horizon": 5, "predicted_workload": [ ...5 floats... ], "trend": "increasing|decreasing|stable" }
```

`trend` via `classify_trend` (`inference.py:27`, 2% relative change);
predictions clamped ≥ 0.

### 5.5 Downstream consumer (context)
The **PPO controller** (`rl/`) consumes forecasts; its observation begins with
`predicted_workload`. Currently the env uses current workload as a placeholder
and exposes `ServerlessEnv.set_forecast()` for the P3 wiring.

## 6. Data pipeline

### 6.1 Sources
- **Intended:** Azure Functions traces (data source only), mapped to the
  required/optional schema.
- **Current:** synthetic `data/sample.py` (no dataset committed; CSV ignored).

### 6.2 Raw data nature (synthetic generator)
`sample_trace` (`data/sample.py:5`): 3 functions
(`fn_checkout`, `fn_search`, `fn_recommend`) with bases `420/265/150`; 30 s
cadence; default 7 days; seed 42; **daily sinusoid** peaking ~14:00; **weekend
factor 0.72**; 7% noise; correlated duration/CPU/memory/containers/cold
starts/latency/P95/power. The diurnal + weekly + bursty shape gives the model
real structure to learn.

### 6.3 Preprocessing (D01–D04)
See the P1 doc for full detail. Summary: chronological sort → dedupe
(`last`) → outlier repair (bounds; CPU/mem ∈ [0,1]) → resample to 60 s
(counts summed, metrics averaged, gaps reindexed) → fill (zeros for counts,
ffill→bfill for metrics) → JSON report at every stage.

### 6.4 Feature engineering
24 columns (3 lag + 12 rolling + 4 temporal + 5 system), per-function trailing
windows, warm-up rows dropped. Normalization deferred to the forecaster.

### 6.5 Leak-safe windowing & scaling (`forecasting/dataset.py`)
- **Split before windowing:** each function's timeline is cut into contiguous
  `[train][val][test]` (`chronological_boundaries:54`); `build_windows:70`
  emits windows fully inside a segment. Input `[t−h, t−1]`, target `[t, t+h−1]`
  — no overlap, no boundary crossing (**T03**).
- **Scaler fit on train rows only** (`dataset.py:169`), persisted for inverse
  scaling.
- Windows built **per function**, then concatenated.

## 7. System integration

### 7.1 Interfaces

| Producer → Consumer | Contract |
|---|---|
| Pipeline → forecaster | `run()` → `(DataFrame, report)`; frame has target + covariates |
| Dataset → model | `X_* (N,30,7)`, `y_* (N,5)`, `scaler`, `target_index` |
| Model → checkpoint | state + `n_features`, `horizon`, `feature_columns`, `target_index`, `scaler_mean/std`, `model_cfg` |
| Checkpoint → inference | `forecast_from_checkpoint(payload, window)` → forecast dict |
| Forecast → controller (P3) | `predicted_workload[5]` → `OBS_NAMES[0]` via `set_forecast()` |

### 7.2 Seams
- Single cadence: `control.interval_seconds` drives resampling and the env clock.
- Channel order preserved between training and inference via the checkpoint.
- Fail-safe: `validate_trace` rejects bad input; short series are skipped; empty
  splits return typed empty arrays.
- Trust boundary: model output is untrusted until downstream validation (P3).

### 7.3 Honest gap
`predicted_workload` in the PPO env currently defaults to current workload. The
TFT is trained and can emit forecasts, but **TFT → state builder → Qwen3 → PPO
is not wired yet** (P3). The `set_forecast` hook and obs index already exist.

## 9. How to train and evaluate (current state)

### 9.1 Is the model trained?
Only **smoke-trained**: checkpoints exist locally (`models/tft_checkpoint.pt`,
`models/ppo_policy.pt`) from short runs (TFT **2 epochs**, PPO **5 episodes**)
on **synthetic** data. They are gitignored and **not** production-quality.
A real training run is `forecast.training.epochs: 8` (config default) on the
data you provide.

### 9.2 Train the TFT
```bash
py -m forecasting.train                 # uses config (8 epochs), prints checkpoint + metrics
py -m forecasting.train --epochs 2 --verbose   # quick smoke run with per-epoch loss
```
The run prints JSON with `train_loss`/`val_loss` history and **held-out
`test_metrics` (MAE/RMSE/MAPE on the inverse-scaled target)**. Checkpoint path:
`forecast.checkpoint_path`.

To train on real data, put the Azure trace CSV somewhere and set:
```yaml
data:
  source: file            # anything != "sample"
  source_path: data/raw/azure_functions_trace.csv
```
then rerun the command. `data.source_path` is not committed.

### 9.3 Evaluate
Evaluation is currently **inside training** (best-val checkpoint + test
metrics). For a standalone check, run the same command with a small epoch count
or import the helpers:
```python
from forecasting.train import train_tft
model, data, history = train_tft(frame, config=config)
print(history["test_metrics"])   # {'mae': ..., 'rmse': ..., 'mape': ...}
```
`forecasting.evaluate` exposes `mae`, `rmse`, `mape`, `regression_metrics`.

### 9.4 Train/evaluate PPO (context)
```bash
py -m rl.train_ppo --episodes 10 --verbose
```
`rl.evaluate_ppo.evaluate_policy(model, env)` reports mean reward, SLA-violation
rate, mean energy/capacity/cold starts/P95; `evaluate_reactive(frame, config)`
runs the reactive baseline on the same env for comparison.

### 9.5 Verification
```bash
py -m pytest      # 54 tests: D01–D04, T01–T04, R01–R04 + component tests
```

## 10. Limitations and roadmap

| Limitation | Impact | Next step |
|---|---|---|
| No real gateway/LB | No live ingestion | P4 deployment + gateway telemetry |
| Synthetic data only | Scores not representative | Load Azure trace via `source_path` |
| Compact TFT (not full TFT) | Possible accuracy gap | Optional upgrade |
| TFT not wired to PPO | Placeholder forecast | P3 state-builder integration |
| Batch-only inference | No streaming adaptation | P5 feedback loop |
| MAPE unstable at low load | Misleading on quiet functions | Prefer MAE/RMSE in reports |
