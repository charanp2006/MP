## 1. Objective

Replace the generic M9 sample handler with small but real containerized
checkout/search/recommend services that expose health, readiness, invocation,
service-specific behavior and Prometheus metrics aligned with the live
dashboards.

## 2. Scope

- Implement service-specific `/invoke` responses selected by `SERVICE_NAME`.
- Add `/health`, `/ready`, `/invoke` (POST) and `/metrics` endpoints.
- Emit `fn_invocations_total`, `fn_request_duration_ms_bucket`,
  `fn_request_duration_ms_sum`, `fn_request_duration_ms_count`,
  `fn_errors_total`, `fn_cold_starts_total`, `fn_energy_w`,
  `fn_active_containers` with `function_name` and `service` labels.
- Harden Dockerfile and Compose with a non-root user, ENV defaults,
  healthchecks and resource limits.
- Update the service registry and add focused in-process HTTP tests.

| File | Purpose |

## 4. Design / data contracts

- `SERVICE_NAME` selects one of `fn_checkout`, `fn_search`, `fn_recommend`;
  an unknown value fails fast. `FUNCTION_NAME` defaults to the hyphenated
  OpenFaaS name (`fn-checkout`, etc.) so dashboard queries match, while the
  `service` label keeps the underscore registry ID.
- `GET /` returns service metadata and the route list. `GET /health` returns
  `status`, `service`, `version`, `uptime_s`, `cold_start`; `GET /ready` returns
  readiness metadata. Health/ready/metrics/root are not counted as invocations.
- `POST /invoke` accepts a JSON object with `payload_class` in
  `small|medium|large` and service-specific fields (`items` for checkout,
  `query`/`limit` for search, `category`/`limit` for recommend). Success returns
  `service`, `accepted`, `payload_class`, `duration_ms` and one of `checkout`,
  `search`, `recommendations`.
- Rejections return `accepted: false` with a structured `error.code` and no
  stack traces. Identity-like fields and raw payload values are never echoed,
  logged or persisted; result IDs are derived hashes.
- `duration_ms` and `fn_energy_w` are deterministic research proxies (no
  sleeping, no real metering): latency comes from a per-service/payload-class
  table plus a one-time cold-start penalty. Histogram buckets match the live
  dashboard (5…1000 ms, `+Inf`). Counters and gauges are process-local and
  lock-protected.

## 5. How to run & verify

```bash
docker compose -f demo/services/docker-compose.yml up --build
curl http://127.0.0.1:8081/health
curl -H 'Content-Type: application/json' -d '{"items":[{"sku":"A1","quantity":2,"unit_price":10.5}]}' http://127.0.0.1:8081/invoke
curl http://127.0.0.1:8081/metrics
python -m pytest tests/test_sample_services.py -q
python -m pytest -q --disable-warnings
git diff --check
```

## 7. Limitations / next steps

- Services are research demonstrations, not production applications.
  `deployment` in the registry explicitly says local container scaffolding with
  no production claims.
- No persistent datastore, real payments, authentication or real user
  information is included; identity-like input fields are ignored.
- Latency and energy values are deterministic proxies for reproducible demos,
  not measurements of container resource use.
- Container builds, Compose healthchecks and OpenFaaS wiring were not executed
  in tests (static config checks only). Deployment/live validation remains in
  the separate P6 live path and runbook.
- Metrics are process-local; scraping/aggregation across replicas is handled by
  the existing Prometheus configuration, not by these services.
