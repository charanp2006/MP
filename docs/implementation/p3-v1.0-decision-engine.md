## 1. Objective

Wire the forecasting output into a **bounded decision loop**:

```
TFT forecast → state builder (L4) → Qwen3/stub planner (L5) → plan validator (L6) → PPO policy → action validator (L9) → SLA guard (L8) → bounded action
```

No component has unrestricted control: Qwen3 is **high-level only** (no infrastructure commands), every plan and action is schema-validated and bounded, and the SLA guard is **independent** of the learned policy.

---

## 2. Runtime choice: stub by default, Ollama for real Qwen3 (record)

| Criterion | A) Deterministic stub | B) Ollama (HTTP) — `qwen3:4b` | C) HF in-process |
|---|---|---|---|
| Real Qwen3 | No | **Yes** | Yes |
| Setup cost | None | Low (`ollama pull qwen3:4b`) | High (multi-GB weights) |
| Python 3.14 risk | None | None (out-of-process) | **High** (wheel/GPU issues) |
| Testability / CI | **Hermetic** | Needs mocking; non-deterministic | Heavy, slow, brittle |
| Latency / footprint | Instant | Seconds; Ollama manages CPU/GPU | Largest RAM/VRAM, slow on CPU |
| Failure handling | Always works | Service may be down | OOM/crash risk |
| Fit for simulation-first prototype | **Best** | **Best for demos/experiments** | Overkill |

**Design:** `agent/planner.py` defines a `Planner` protocol. `StubPlanner` is the default (and used by all tests). `Qwen3OllamaPlanner` posts to `http://localhost:11434/api/chat` with `format: "json"`, `temperature: 0`, `num_predict: 256`. `FallbackPlanner` catches timeouts/parse errors and falls back to the stub (never crashes the loop). Config in `configs/project.yaml`:

```yaml
agent:
  runtime: stub        # stub | ollama
  model: qwen3:4b
  base_url: http://localhost:11434
  timeout_s: 30
  temperature: 0.0
  num_predict: 256
  high_demand_ratio: 1.10
  low_demand_ratio: 0.90
```

**Safety:** Qwen3 output is untrusted (schema + plan validator). Infrastructure commands are forbidden by the prompt and rejected by schema validation (`extra="forbid"`). LLM reasoning quality is **not measured** here — only bounded integration and failure handling.

## 4. Design / data contracts

### 4.1 State snapshot (`agent/schemas.py`)
Required: `forecast_workload`, `forecast_peak`, `current_workload`, `trend`, `cpu_utilization`, `memory_utilization`, `active_containers`, `p95_latency_ms`, `cold_start_rate`, `energy`, `sla_threshold_ms`, `sla_margin_ms`. `metadata` is stringified and treated as untrusted (Q05).

### 4.2 Plan (`docs/design.md §9`)
```json
{
  "strategy": "NoOp | PreWarm | ScaleOut | Reuse | ScaleIn | Terminate",
  "desired_capacity_change": 0,
  "priority": "sla | energy | cost | balanced",
  "urgency": "low | medium | high",
  "reason": "...",
  "constraints_respected": true
}
```
No extra fields; infrastructure commands are rejected. Strategy normalization accepts common variants.

### 4.3 Validation rules
- **Plan validator:** approved strategy set, `constraints_respected`, `|change| ≤ max_change_per_cycle`, direction matches strategy, target capacity within `[min,max]`. On failure, loop falls back to stub + `NoOp` if still invalid.
- **Action validator:** action in canonical set, authorization required, plan-consistency at high urgency, bounded to capacity limits.
- **SLA guard:** if action is `ScaleIn`/`Terminate` and `P95 ≥ sla_threshold - safety_margin_ms` → reject/defer to `NoOp` (independent of learned policy).

### 4.4 Decision record (audit)
Each cycle records forecast, state, plan (and validity/reason), PPO action, final action, guard/action codes, fallback flag and authorization (matches `docs/security.md §14`).

## 5. How to run & verify

### 5.1 Tests (Q01–Q06 + integration)
```bash
py -m pytest tests/test_agent.py tests/test_orchestrator.py -v
py -m pytest -q
```

Coverage: valid context, high/low demand, SLA-risk priority, prompt injection treated as data, invalid output → fallback, schema rejection of commands, Ollama adapter (parse/timeout/fail), state builder, plan validator bounds/direction, SLA guard, action validator, integrated loop, override by guard, unauthorized → NoOp, episode smoke. **All tests pass (including pre-existing P1/P2).**

### 5.2 Smoke run (simulator)
```bash
py -m orchestrator.decision_loop --steps 8 --policy none
py -m orchestrator.decision_loop --steps 8 --policy checkpoint
```
Uses the pipeline+env, builds forecast from the timeline, runs the full loop, prints an auditable JSON record (plan → PPO action → guard/validation → final action).

### 5.3 Use real Qwen3 via Ollama (optional)
```bash
ollama pull qwen3:4b
ollama serve   # http://localhost:11434
```
Set `agent.runtime: ollama` in `configs/project.yaml` (or `--runtime ollama`) and run the loop. If Ollama is down or returns invalid JSON, `FallbackPlanner` switches to the deterministic stub automatically.
